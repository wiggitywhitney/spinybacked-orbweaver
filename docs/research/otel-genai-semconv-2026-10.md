## Summary

Every `gen_ai.*` semantic convention is still **Development** status (only referenced core attributes such as `error.type` are Stable). Since core semconv v1.42.0 (2026-06-12) they live in a separate repository, `open-telemetry/semantic-conventions-genai`, which has **no tagged release** as of 2026-10-05. `gen_ai.system` was renamed to `gen_ai.provider.name` in **v1.37.0**. The token attributes were renamed earlier, in **v1.27.0** (`gen_ai.usage.prompt_tokens` became `gen_ai.usage.input_tokens`). The conventions attach `gen_ai.provider.name` (Required) and the full `gen_ai.request.*`, `gen_ai.response.*` and `gen_ai.usage.*` set to the **inference span**: the client call to the model itself. Orchestration spans are defined as different GenAI span types with much smaller attribute sets. An `invoke_workflow` span, which the spec says fits a LangGraph graph invocation, carries only `gen_ai.operation.name`, `gen_ai.workflow.name`, `gen_ai.conversation.id`, `error.type` and opt-in messages. It has no model, provider or usage attributes. The normative text gives no rule for model, provider or usage attributes on an ordinary, non-GenAI application span that wraps a model call. It does explicitly allow `gen_ai.conversation.id` on "GenAI and other spans", and its non-normative examples show an encompassing application span with no `gen_ai.*` attributes. Independent projects (LiveKit, Langfuse users) found that wrappers which set `gen_ai.operation.name` or model and usage attributes get counted by backends as extra LLM calls. Prompts, system instructions and completions are captured as **opt-in** attributes (`gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`) on spans or on the opt-in `gen_ai.client.inference.operation.details` event. The spec says instrumentations SHOULD NOT capture content by default.

## Surprises & Gotchas

- 🟢 **`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` takes different values in different languages.** Python's `opentelemetry-util-genai` (experimental mode) takes `NO_CONTENT`/`SPAN_ONLY`/`EVENT_ONLY`/`SPAN_AND_EVENT`, and logs a warning on `true`. OTel JS `@opentelemetry/instrumentation-openai` 0.20.0 takes a boolean `true`, ignores `OTEL_SEMCONV_STABILITY_OPT_IN`, and emits message content only as log records. One exception: its Responses API path also writes `gen_ai.system_instructions` to the span without checking the opt-in (see Q4). The spec mentions the variable only as an example ("for example") and defines no values for it.
- 🟢 **The GenAI conventions left the main semconv repository.** Core v1.42.0 deprecated every `gen_ai.*` definition there. The pages on opentelemetry.io and in the core repository's `docs/gen-ai/` now read "Moved". The new repository's `CHANGELOG.md` has only an "Unreleased" section and no release tags. **There is no semconv version number to cite for current GenAI behavior**: the last versioned definition is core v1.41.x, and anything newer is "main of semantic-conventions-genai at commit X".
- 🟢 **`invoke_workflow` is a newer operation, and the spec names LangGraph graph invocation as its example.** That matters for finding 1, because commit-story-v2's wrapper span sits around a LangGraph node. The workflow span carries no model, provider or token attributes.
- 🟢 **`gen_ai.provider.name` was removed from the internal `invoke_agent` span.** It is Required on inference (model-call), embeddings, fetch-response, `create_agent` client and `invoke_agent` client (remote agent service) spans. It is Conditionally Required on retrieval ("When applicable") and memory ("If the operation is handled by a named external GenAI provider or service") spans, and not defined on the internal `invoke_agent`, `invoke_workflow`, plan or execute-tool spans. Issue #178 (closed 2026-08-28), which prompted the removal, named LangGraph and called copying the inner LLM's provider onto the agent span a leak of "implementation details of the inner LLM call". Training-data examples that put the provider on every agent span are out of date.
- 🟢 **Cache token attributes on the internal agent span were removed on purpose**, because aggregating them across models "makes them misleading". The stated alternative is to aggregate from `gen_ai.inference.client` spans. This applies to the cache-breakdown attributes only: total `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` remain Recommended on the internal agent span (see the Q3 table).
- 🟢 **Rename: `gen_ai.usage.cache_creation.input_tokens` became `gen_ai.usage.cache_write.input_tokens`.** This rename is in the new repository only, unreleased. Core v1.40.0 introduced the old name.
- 🟢 **The GenAI repository carries no deprecated entries.** `gen_ai.system` and `cache_creation` are simply absent there, with no `renamed_to`. Only core v1.41.x and opentelemetry.io map old names to new ones.
- 🟢 **The `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` transition notice is missing from the new repository's README.** Core v1.41.0's README carried it, and it said that instrumentations which emitted v1.36.0 or earlier keep emitting the old conventions **by default**. Libraries that implement that plan, which may include Traceloop (to be checked in M2), emit `gen_ai.system` unless the opt-in is set.
- 🟢 **Anthropic `input_tokens` excludes cached tokens.** **Source says:** "Anthropic `input_tokens` excludes cached tokens. Compute: `gen_ai.usage.input_tokens = input_tokens + cache_read_input_tokens + cache_write_input_tokens`" ([anthropic.md line 188](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/anthropic.md?plain=1#L188)). **Corroborated by:** pipecat [issue #5993](https://github.com/pipecat-ai/pipecat/issues/5993) (2026-10-01): "`AnthropicLLMService` and `AWSBedrockLLMService` report `prompt_tokens` net of the prompt cache … So for these services the span leaves the cached tokens out of `gen_ai.usage.input_tokens`". A wrapper span that copies the SDK's `usage.input_tokens` under-reports. *Re-verified 2026-10-06.*
- 🟢 **`gen_ai.prompt` and `gen_ai.completion` were deprecated in v1.28.0 with no direct replacement. The per-message events (`gen_ai.user.message`, `gen_ai.choice`, …) were deprecated in v1.37.0.** Older guides still show both.
- 🟢 **The token rename (`prompt_tokens` → `input_tokens`) is v1.27.0, not v1.28.0**, which an earlier version of this document stated.

🟢 **High (spec) / 🟡 (application to LangGraph): what the workflow span says about LangGraph and nested graphs.**
**Source says:** "The workflow span SHOULD be reported for operations that trigger the execution of composable processes (e.g., graphs, orchestrators) coordinating multiple agents or GenAI calls. Framework-specific semantic conventions SHOULD define which operations to report as workflows …" Examples include "**LangChain / LangGraph**: `*Graph*.invoke(...)`". ([gen-ai-agent-spans.md lines 815–834](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-agent-spans.md?plain=1#L815-L834))
**Corroborated by (purpose only):** "A user-facing entry point that coordinates several agents or GenAI calls" and "Not for a standalone agent." ([Matthews Wong](https://www.matthewswong.com/en/blog/opentelemetry-genai-agent-spans-tracing/)). No second source discusses the sub-graph-as-node rule, so it is 🟡 spec-only.
**Verified locally:** no framework-specific LangGraph convention exists. At `cb10b70c15c0`, "LangGraph" appears in exactly one place across all 192 Markdown and YAML files: the example line above.
**Interpretation (re-checked, still for M4):**
- A LangGraph graph invocation (`graph.invoke(...)`) fits `invoke_workflow`, and so does a node whose body invokes an application-defined sub-graph.
- A node whose body runs a LangChain agent may fit the internal `invoke_agent` span, whose spec examples are "LangChain agents, CrewAI agents". This possibility was not raised on 2026-10-05.
- An ordinary node that calls a chat model once is neither of those, and no GenAI span type fits it.
- 🟡 An open proposal, issue #477 (see Q1), may merge `invoke_agent` and `invoke_workflow`.

🟡 **Medium (corrected 2026-10-06): the conventions say almost nothing about non-GenAI application spans, but not literally nothing.** The 2026-10-05 text said neither spans document mentions an application span that wraps a model call. Two passages do touch on it:
1. **Conversation id on other spans.** **Source says:** "Application developers that manage conversation history MAY add conversation id to GenAI and other spans or logs using custom span or log record processors or hooks provided by instrumentation libraries." ([gen-ai-spans.md lines 153–155](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-spans.md?plain=1#L153-L155)) This is the only `gen_ai.*` attribute the spec explicitly allows on non-GenAI spans. **Corroborated by:** LiveKit's [PR #7396](https://github.com/livekit/agents/pull/7396) (open) stamps "`gen_ai.conversation.id` on every span, not only the GenAI ones", because "A backend that groups a session by the attribute drops any span without it".
2. **An encompassing span in the non-normative examples.** **Source says:** "The relationship between below spans depends on how user application code is written. They are likely to be siblings if there is an encompassing span." ([examples-llm-calls.md lines 335–336](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/non-normative/examples-llm-calls.md?plain=1#L335-L336)) In these examples the encompassing application span is not given any `gen_ai.*` attributes; only the client spans carry provider, model and usage. This is non-normative.

Apart from those two passages, the normative text defines no rule for model, provider or usage attributes on a non-GenAI parent span. That makes "the wrapper carries no `gen_ai.*` attributes" a **policy choice** for M4, which the spec supports but does not mandate. Independent sources state the same convention and call it implicit:
- **Source says:** "The convention — cost and tokens live only on the actual LLM call — is implicit, not specified." and "every platform puts cost and tokens on the actual LLM call, not on the orchestration wrapper" ([Vladimir, "When agent trace metrics lie", DEV, 2026](https://dev.to/khan5v/when-agent-trace-metrics-lie-the-span-tree-double-counting-problem-3lhp))
- **Source says:** "Token counts and cost belong to the `chat` span …" and "repeating them here would double-count them in any query that sums over spans", referring to the application's `generate_response` wrapper, which "carries only the stage marker and the RAG context size" ([base14 Spring AI guide](https://docs.base14.io/guides/ai-observability/spring-ai-llm-observability/))

🟢 **High (new 2026-10-06): a wrapper span that sets `gen_ai.operation.name` or model attributes gets misclassified by backends, which is finding 1's failure.** Two independent projects hit it:
- **LiveKit.** **Source says:** "`llm_fallback_adapter` and its provider request both report `chat`, so observability backends can count an extra LLM call. Omit the adapter's operation name while preserving its metadata and fallback events." ([livekit/agents PR #7373](https://github.com/livekit/agents/pull/7373), merged 2026-09-22) The follow-up says: "`gen_ai.usage.*` still lands on both the adapter span and the `llm_request` beneath it, and a backend summing tokens across spans counts every call twice. The adapter now leaves the counts to the provider call" ([PR #7396](https://github.com/livekit/agents/pull/7396), open).
- **Microsoft Agent Framework in Langfuse.** **Source says:** "the framework's `invoke_agent` spans carried a `gen_ai.request.model` attribute", so "both the orchestration span and the nested LLM calls got counted, doubling the totals." ([Vladimir, DEV](https://dev.to/khan5v/when-agent-trace-metrics-lie-the-span-tree-double-counting-problem-3lhp)) The original report is [langfuse discussion #11252](https://github.com/orgs/langfuse/discussions/11252) (2025-12-20, unanswered).

**Interpretation:** this matches how Datadog classified commit-story-v2's wrapper. Whether Datadog keys on `gen_ai.operation.name` specifically is still M3's question.

**Interpretation, for M4 to decide (not a source claim):**
- When the conventions set `gen_ai.operation.name: chat`, `gen_ai.provider.name` and `gen_ai.request.model`, they describe the span **for the model call itself**. A span that sets `chat` claims to be an inference span, and backends treat it as one (LiveKit, Langfuse).
- If a library such as `@traceloop/instrumentation-langchain` emits the inference span, an application wrapper that also sets `chat` and partial request attributes duplicates the classification. For Anthropic it may also report token counts that disagree with the inference span's (see the Anthropic cached-token rule).
- A wrapper can legitimately carry a GenAI identity in three cases:
  - `invoke_workflow`: a graph run, or a node that invokes an application-defined sub-graph.
  - internal `invoke_agent`: an in-process agent run.
  - `execute_tool`: an application-executed tool.

  None of these carries `gen_ai.provider.name`. `invoke_workflow` and `execute_tool` carry no model or usage attributes either.
- An ordinary LangGraph node gets no `gen_ai.*` attributes from the conventions, apart from the optional `gen_ai.conversation.id` that the spec allows on any span.
- When **no** library covers the call, the application span that directly wraps the SDK call is effectively the inference span, and the inference requirements apply to it: `operation.name`, `provider.name` and `request.model`, set at span creation.

### Q4. Capturing prompts, system instructions and completions

*Re-checked 2026-10-06 (M1b, question 4). Spec at `cb10b70c15c0`. Implementation behavior was read from source with `gh api`: `open-telemetry/opentelemetry-python-contrib` at `2d9c5d05ee8c` and `open-telemetry/opentelemetry-js-contrib` at `2729b781e491`.*

🟢 **High: off by default, and opt-in.**

**Source says:** "Model instructions, user messages, and model outputs are considered sensitive and are often large in size. … OpenTelemetry instrumentations SHOULD NOT capture them by default, but SHOULD provide an option for users to opt in." The usage patterns it lists are:
- "1. [Default] Don't record instructions, inputs, or outputs."
- "2. Record instructions, inputs, and outputs on the GenAI spans using corresponding attributes (`gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages`). This approach is best suited for situations where telemetry volume is manageable and either privacy regulations do not apply or the telemetry storage complies with them, for example, in pre-production environments."
- "3. Store content externally and record references on the spans. This pattern is recommended in production environments where telemetry volume is a concern or sensitive data needs to be handled securely."

([gen-ai-spans.md lines 1294–1331](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-spans.md?plain=1#L1294-L1331))

**Corroborated by:** "Treat prompt and response bodies as opt-in, not default." and "Leave content capture off by default in production." ([OpenObserve, Simran Kumari, 2026-08-11](https://openobserve.ai/blog/opentelemetry-genai-semantic-conventions/)); "the contents of the prompt, completion, function arguments and return values are not captured by default." ([opentelemetry-instrumentation-openai-v2 2.4b0 on PyPI, 2026-05-01](https://pypi.org/project/opentelemetry-instrumentation-openai-v2/))
**Source says (core v1.37.0):** "Instead of per-message events, we now have `gen_ai.system_instructions`, `gen_ai.input.messages`, and `gen_ai.output.messages` attributes that can appear on GenAI spans or the new `gen_ai.client.inference.operation.details` event. New attributes are not recorded by default when content capturing is disabled." ([core CHANGELOG lines 581–585](https://github.com/open-telemetry/semantic-conventions/blob/v1.44.0/CHANGELOG.md?plain=1#L581-L585))
**Corroborated by:** "per-message events replaced by `gen_ai.input.messages`, `output.messages`, `system_instructions` attributes" ([John Hodge](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/))

🟢 **High: where content goes, and in what format.**
- **Opt-In on every span type that carries content.** `gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages` and `gen_ai.tool.definitions` are `opt_in` on the inference span and on both `invoke_agent` spans, through the `attributes.gen_ai.content` group ([spans.yaml L83–L93](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/model/gen-ai/spans.yaml#L83-L93)). The workflow span has input and output messages as Opt-In, and execute tool has `gen_ai.tool.call.arguments`/`result` as Opt-In. *Corrected 2026-10-06: the 2026-10-05 text said only the messages attributes were also Opt-In on agent spans. The whole content group is.* Konishi corroborates the agent-span part: `gen_ai.system_instructions` appears on "Inference, agent, and create-agent spans."
- **The event is also Opt-In.** `gen_ai.client.inference.operation.details` has "**Requirement level:** Opt-In" ([gen-ai-events.md line 37](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-events.md?plain=1#L21-L37)). 🟡 The event's requirement level is spec-only. OpenObserve describes content as "structured log-based events, correlated back to the originating span via trace_id and span_id" but does not name the level.
- **JSON schemas and the `parts` array.** Messages follow the inputs and outputs JSON schemas (`gen-ai-input-messages.json`, `gen-ai-output-messages.json`) and use a `parts` array. The events doc's example is `{"role": "user", "parts": [{"type": "text", "content": "Weather in Paris?"}]}`. 🟡 The `parts` format is spec-only in this document, and the global gotcha rule `otel-semconv-gotchas.md` states the same thing.
- **Structured form versus JSON string.** **Source says:** "When the attribute is recorded on events, it MUST be recorded in structured form. When recorded on spans, it MAY be recorded as a JSON string if structured format is not supported and SHOULD be recorded in structured form otherwise." Also: "Recording structured attributes is supported on events (or logs) and may not yet be supported on spans. … If structured attributes are not yet supported on spans in a given language, the corresponding attribute value SHOULD be serialized to JSON string on spans and recorded in its structured form on events." ([gen-ai-spans.md lines 1342–1352](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-spans.md?plain=1#L1342-L1352)) 🟡 spec-only. **Interpretation:** in JavaScript, where span attributes cannot hold nested objects, content on spans is a JSON string.
- **Text-only system instructions.** `gen_ai.system_instructions` part types are limited to text (257.breaking).
- **Upload hooks.** An external-storage upload hook "SHOULD operate independently of the opt-in flags", and the spec still has "TODO: document a common approach to record references to externally stored content." 🟡 spec-only. This is new on 2026-10-06.

## Conflicting Findings (Q4)

- **OpenObserve says:** content is "structured log-based events, correlated back to the originating span via trace_id and span_id", "rather than expecting it to appear as a span attribute." ([OpenObserve](https://openobserve.ai/blog/opentelemetry-genai-semantic-conventions/))
- **The spec says:** pattern 2 is "Record instructions, inputs, and outputs on the GenAI spans using corresponding attributes", and the attributes are Opt-In on spans ([gen-ai-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-spans.md?plain=1#L1311-L1320)).
- **Interpretation:** the spec wins on what is allowed, since both placements are valid. OpenObserve describes what some implementations do; the JS OpenAI package, for example, sends message content only to log records (apart from the ungated `gen_ai.system_instructions` span attribute on its Responses path). Where content lands is per-package, which is why M2 reads it from installed code.

## Conflicting Findings (Q1)

- **A secondary blog says** some posts claim GenAI "went stable" in "OTel 1.30" (reported in [John Hodge](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/) as a claim the author refutes).
- **The primary source says** "Status: Development" throughout ([genai README](https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/README.md)).
- **Interpretation:** the primary source wins. Nothing is stable.

## Recommendation (input to M4; the decisions belong to Whitney)

1. When a library emits the inference span, treat the model-call-level `gen_ai.*` attributes (`operation.name` = chat/text_completion/generate_content, `provider.name`, `request.*`, `response.*`, `usage.*`) as belonging only to that span. Do not copy them onto application wrapper spans.
2. When no library covers the call, the span that directly wraps the SDK call should carry the inference attributes, with `provider.name` set at span creation, and `request.model` set at span creation when it is available (the spec makes it Conditionally Required, "If available").
3. A wrapper around a graph run, or around a node that invokes an application-defined sub-graph, may legitimately be an `invoke_workflow` span, but it then carries only workflow attributes. A node that runs a LangChain agent may fit the internal `invoke_agent` span. M4 should decide whether spiny-orb ever suggests either, given that libraries such as Traceloop LangChain may already emit workflow or agent spans (M2 checks), and that open issue #477 may merge the two span types.
4. Content capture: the spec default is off. That gives M4 decision 6 a spec-backed default of opt-in. The variable that turns capture on, and its values, are per package. JS OpenAI takes `true`; Python experimental mode takes `SPAN_ONLY`/`EVENT_ONLY`. The generated template must therefore use the value each recommended package reads (M2), not one value for all.

## Caveats

- Everything is Development and the new repository is unreleased, so these definitions can change without a version bump. Re-check `semantic-conventions-genai` main before M5 and M6 write code against it.
- The tables above are from main at `cb10b70c15c0`. Libraries pinned to core v1.36 or v1.37 emit older shapes.
- Q3's finding that the normative text gives no rule for model, provider or usage attributes on application spans is from the spec. Two independent sources (Vladimir on DEV, base14) describe the same convention as "implicit, not specified", and LiveKit's and Langfuse users' backend problems show what goes wrong when a wrapper carries those attributes.
