## Findings

### Summary

Datadog LLM Observability is now branded **Agent Observability**. Its URLs, the `llmobs` header value and the `DD_LLMOBS_*` names are unchanged. It converts OTel spans that follow the GenAI semantic conventions v1.37+ into its own span schema. It also accepts OpenInference spans and Langfuse spans as of October 2026, and maps OpenLLMetry's older attribute names as fallbacks. According to the current docs, any Datadog OTel trace-ingestion path works: direct OTLP intake, the Datadog Agent's OTLP receiver, the upstream Collector, or DDOT. The authoritative page is `llm_observability/instrument/otel_instrumentation`, whose source is pinned below.

The finding that matters most for M3 is that Datadog's docs changed on 2026-10-05. Conversion went from automatic, with a `dd_llmobs_enabled=false` opt-out, to wording that says "To enable LLM Observability conversion, set the `dd_llmobs_enabled` attribute to `true`." The OTel compatibility page still says conversion is automatic. commit-story-v2 sets neither the attribute nor the `dd-otlp-source=llmobs` header, yet its spans reached Agent Observability on 2026-10-02. The live check has to establish whether that still happens.

### Surprises & Gotchas

**Conversion may now be opt-in through `dd_llmobs_enabled=true`. Datadog's own pages disagree.** 🟡 medium
- **Source says (OTel instrumentation page, current):** "To enable LLM Observability conversion, set the `dd_llmobs_enabled` attribute to `true`. Setting this attribute on any span in a trace enables conversion of the trace's generative AI spans. An explicit `false` on any span prevents conversion of the entire trace." ([source at `e91e7614`](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/llm_observability/instrument/otel_instrumentation.md); confirmed on the [live page](https://docs.datadoghq.com/llm_observability/instrument/otel_instrumentation/) on 2026-10-07)
- **Source says (the same section before 2026-10-05):** "If you'd only like your generative AI spans to remain in APM and not appear in Agent Observability, you can disable the automatic conversion by setting the `dd_llmobs_enabled` attribute to `false`." ([PR #40272 diff](https://github.com/DataDog/documentation/pull/40272), merged 2026-10-05T18:44:41Z)
- **Source says (OTel compatibility page, last changed 2026-09-15):** "OpenTelemetry traces that have generative AI attributes are automatically converted into Agent Observability traces. To disable this conversion, see Disabling Agent Observability conversion." ([source at `e91e7614`](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/opentelemetry/compatibility.md))
- **Interpretation:** PR #40272's description says only that it replaces the disabling section with enabling instructions. It gives no reason and does not say whether the product's default changed or the old text was wrong. It does not say whether the `dd-otlp-source=llmobs` header path converts without the attribute either. The compatibility page now links to a heading ("Disabling…") that no longer exists. Treat the default as **unknown** until the live check shows it. This bears directly on M4 decision 4: if conversion is opt-in, the generated template may need to set or document `OTEL_RESOURCE_ATTRIBUTES=dd_llmobs_enabled=true`.

**OpenInference is now supported, which reverses the June finding.** 🟢 high
- **Source says:** "Agent Observability supports ingesting OpenTelemetry traces that follow either the OpenTelemetry 1.37+ semantic conventions for generative AI or the supported OpenInference semantic conventions" and "OpenInference spans are supported." ([source](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/llm_observability/instrument/otel_instrumentation.md); [live page](https://docs.datadoghq.com/llm_observability/instrument/otel_instrumentation/))
- **Interpretation:** The 2026-06-23 Watch It Burn spike quoted "OpenInference is not supported." That no longer holds. M2's research doc and M4 decision 3 call `@arizeai/openinference-*` a non-starter because it emits OpenInference names instead of `gen_ai.*`. That is still true of the names, but the reason it mattered for Datadog is gone. Langfuse native instrumentation is also supported now.

**Any Datadog OTel trace path works. The `dd-otlp-source=llmobs` header is shown as one option, not a requirement.** 🟡 medium
- **Source says:** "Any method Datadog supports for ingesting OpenTelemetry traces works with Agent Observability. For the full list of supported ingestion paths, see OpenTelemetry feature compatibility. The following is one way to configure it." ([source](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/llm_observability/instrument/otel_instrumentation.md)) The compatibility table marks Agent Observability as supported for all four setups: Datadog SDK + DDOT, OTel SDK + DDOT, OTel SDK + upstream Collector, and direct OTLP ingest ([source](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/opentelemetry/compatibility.md)).
- **Second source:** Datadog's launch blog (2025-12-01) lists "directly from your OTLP exporter to Datadog's OTLP intake endpoint", "via the Datadog Agent with OTLP ingest enabled", and "through the OpenTelemetry Collector (including the Datadog Distribution of the OpenTelemetry Collector)" ([blog](https://www.datadoghq.com/blog/llm-otel-semantic-convention/)). Both are Datadog sources, so this is not independent corroboration. The independent evidence is commit-story-v2's 2026-10-02 run, whose wrapper span appeared in Agent Observability through the upstream Collector's `datadog` exporter with no header (see "commit-story-v2's path" below).
- **Interpretation:** This resolves the June spike's open question of whether spans sent through the Collector's `datadog` exporter reach Agent Observability: they did on 2026-10-02. It is medium confidence because the opt-in change above may affect non-header paths after 2026-10-05.

**Datadog's direct OTLP trace intake is no longer marked Preview.** 🟡 medium
- **Source says:** the traces intake page now opens with "Datadog's OpenTelemetry Protocol (OTLP) traces intake API endpoint allows applications, managed platforms, and OpenTelemetry Collectors to send traces to Datadog over OTLP HTTP," and has no Preview notice. It supports `http/protobuf` and `http/json`, and "`grpc` is not supported." Trace metrics need the `compute_stats=true` header. ([source](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/opentelemetry/setup/otlp_ingest/traces.md))
- **Interpretation:** This repo's `docs/research/otel-to-datadog-forwarding.md` (2026-06-06) says the traces endpoint "requires contacting a Customer Success Manager." That is now stale. It is one source, the absence of a notice, so medium confidence.

**Datadog now recommends `otlp_http` over the contrib `datadog` exporter for new Collector setups.** 🟢 high
- **Source says:** "For new OpenTelemetry Collector configurations, Datadog recommends the OTLP HTTP exporter and `span_metrics` connector setup. The Datadog Exporter and Datadog Connector remain supported, and existing configurations do not need to migrate." ([datadog_exporter.md at `e91e7614`](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/opentelemetry/setup/collector_exporter/datadog_exporter.md), changed in commit `ffdb63ace042` on 2026-09-15). The Collector setup page's examples all use `otlp_http` ([collector_exporter/_index.md](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/opentelemetry/setup/collector_exporter/_index.md)).
- **Interpretation:** This is not a blocker, because the `datadog` exporter "remain[s] supported". It is relevant if M4 recommends a Collector setup in spiny-orb's docs.

**A trace with no GenAI marker attribute is dropped from Agent Observability entirely. Observed spans also contradict the doc's per-span rule: a span whose only `gen_ai.*` attribute was the numeric `gen_ai.request.temperature`, and which had no marker, was dropped.** 🟡 medium (doc added 2026-09-11; observation and the PR description, see "Span classification (M3 question 2)", which also says why the cause is not settled)
- **Source says:** "Agent Observability requires at least one of these attributes on a span. If no span in a trace has one, the whole trace is dropped before reaching Agent Observability: gen_ai.operation.name, gen_ai.provider.name, openinference.span.kind, langfuse.observation.type, gen_ai.system (deprecated). Spans without any `gen_ai.*` attribute are also dropped individually, even in a trace that qualifies." ([source](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/llm_observability/instrument/otel_instrumentation.md), added in commit `a5a73c781b33`)
- **Interpretation:** spiny-orb's application spans, such as `commit_story.ai.generate_summary` without `gen_ai.*`, never appear in Agent Observability; they stay in APM. Setting `gen_ai.operation.name` on a wrapper is what pulled it into Agent Observability in finding 1. The same runs' `commit_story.ai.generate_dialogue` span carried `gen_ai.request.temperature` without a marker and did not appear at all, which contradicts the doc's second sentence (see Conflicting Findings).

### Ingestion paths

The four documented paths, all marked as supporting Agent Observability:

1. **Direct OTLP intake.** `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf`, endpoint `otlp_trace_endpoint` for the site (for example `https://otlp.datadoghq.com/v1/traces`), and headers `dd-api-key=<KEY>,dd-otlp-source=llmobs`. The Python examples also send an optional `dd-ml-app` header.
2. **Datadog Agent OTLP receiver.** Traceloop's own Datadog page describes only this path, setting `TRACELOOP_BASE_URL=http://<datadog-agent-hostname>:4318` after enabling the Agent's OTLP HTTP receiver ([Traceloop docs](https://www.traceloop.com/docs/openllmetry/integrations/datadog)). That page never names Agent Observability or APM.
3. **Upstream Collector** (`otlp_http` recommended, `datadog` exporter still supported).
4. **DDOT.**

### commit-story-v2's path (the M3 live check runs on it)

Read-only checks on 2026-10-07:
- `examples/instrumentation.js` exports traces with `OTLPTraceExporter` to `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT || 'http://localhost:4318/v1/traces'` with no `dd-otlp-source` header, and sets no `dd_llmobs_enabled`.
- Port 4318 is held by `otelcol-contrib` **0.154.0**, running `spinybacked-orbweaver-eval/evaluation/is/otelcol-config.yaml`. Its traces pipeline exports to `[file, datadog, spanmetrics, datadog/connector]`, and the `datadog` exporter sets only `api.site`.
- The local Datadog Agent (7.83.0) has OTLP enabled on gRPC 4317 only, so it is not in the trace path.
- So the path is **OTel SDK → upstream Collector → contrib `datadog` exporter → Datadog**. That is path 3, with no LLM-specific header or attribute. On 2026-10-02, spans on this path appeared in Agent Observability (finding 1, trace `d6ea4168a7bbbc3697b57fcdb4ea6509`), so conversion was automatic there on that date.

**Implication for the live check:** if LangChain spans from a post-2026-10-05 commit do not appear in Agent Observability, check the opt-in change before suspecting Traceloop. Rerun with `OTEL_RESOURCE_ATTRIBUTES=dd_llmobs_enabled=true` to separate the two. The opposite result would also be informative: spans that appear without the attribute show the "enable" wording is not a default change on this path.

| `_dd.ml_obs.metadata` (Datadog-specific) | merged into `meta.metadata`; `model_name` and `model_provider` reserved | n/a | Datadog-only. Generated instrumentation should not use it, per the OTel-API-only packaging rule. |

**Interpretation for M4.**
- Decision 1: the classification trigger is `gen_ai.operation.name` with an LLM value. *(Revised by M3 question 2.)* This bullet first inferred that a wrapper setting only `gen_ai.request.temperature` would be kept as a `workflow` span. The observed `generate_dialogue` span shows the opposite: such a wrapper is dropped from Agent Observability. See "Span classification (M3 question 2)".
- Decision 3: for Datadog, the old-set packages (cohere, together, vertexai) are not invisible, because the OpenLLMetry fallbacks pick up `gen_ai.system`, `llm.request.type` and the indexed prompts. Each span gets a "Missing model provider" warning, and the tokens land in `prompt_tokens`/`completion_tokens` rather than `input_tokens`/`output_tokens`.
- Decision 6: what Agent Observability shows as content depends on where each package writes it. Span attributes are read; log records are not listed.

### Span classification (M3 question 2)

*Sources: the "Attribute mapping reference", the per-convention "Span kind resolution" tables and the "Mapping warning reference" of the pinned OTel instrumentation page ([source at `e91e7614`](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/llm_observability/instrument/otel_instrumentation.md)); the PR that added the drop rules ([DataDog/documentation PR #39854](https://github.com/DataDog/documentation/pull/39854)). Observed second source, read 2026-10-07: `search_llmobs_spans` over `ml_app: commit-story` from 2026-10-01 to 2026-10-07, which returned 48 spans from 24 APM traces, and `get_datadog_trace` with `extra_fields: ["gen_ai.*", "llm.*"]` on APM traces `d6ea4168a7bbbc3697b57fcdb4ea6509` and `d6545448c81bca9d2bd5406ba27dae83` (31 spans each). Independent third-party corroboration: [livekit/agents issue #4639](https://github.com/livekit/agents/issues/4639). Datadog's converter is not public, so the precedence rules below are doc-only unless marked observed.*

**Answer.** Classification has two stages. First, a span has to survive the drop rules: its trace must contain a marker attribute, and the span itself must carry something more than a numeric `gen_ai.*` attribute (observed; whether that something must be a marker is not settled, see below). Second, the surviving span's kind comes from `gen_ai.operation.name` alone. If the value is `chat`, `generate_content`, `text_completion` or `completion`, the span is an LLM span. In finding 1, `gen_ai.operation.name: chat` on the wrapper did both jobs: it qualified the trace, kept the span, and made it `llm`.

**Stage 1: which spans survive.** 🟡 medium
- **Source says:** "Agent Observability requires at least one of these attributes on a span. If no span in a trace has one, the whole trace is dropped before reaching Agent Observability: gen_ai.operation.name, gen_ai.provider.name, openinference.span.kind, langfuse.observation.type, gen_ai.system (deprecated). Spans without any `gen_ai.*` attribute are also dropped individually, even in a trace that qualifies." ([source](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/llm_observability/instrument/otel_instrumentation.md))
- **PR #39854's description says:** "adding mapping requirements to Otel instrumentation documentation specifically that for a span to be generated it requires one of a list of attributes." ([PR #39854](https://github.com/DataDog/documentation/pull/39854), merged 2026-09-11)
- **Observed:** In both full APM traces, three spans carry `gen_ai.*`:

  | APM span | `gen_ai.*` on the APM span | In Agent Observability? |
  |---|---|---|
  | `commit_story.ai.generate_summary` | `gen_ai.operation.name: chat`, `gen_ai.request.temperature: 0.7` | yes, `span_kind: llm` |
  | `commit_story.ai.generate_technical_decisions` | `gen_ai.operation.name: chat`, `gen_ai.request.temperature: 0.1` | yes, `span_kind: llm` |
  | `commit_story.ai.generate_dialogue` | `gen_ai.request.temperature: 0.7` only | **no** |

  A search by `generate_dialogue`'s span ID (`5181306985314646393`) returns nothing. Searches for `span_name: commit_story.ai.generate_dialogue` and for `span_kind: workflow` across all of `ml_app: commit-story` from 2026-10-01 to 2026-10-07 also return nothing. A control search with `span_kind: llm` over the same window does return spans, so the filters work. All 48 converted spans are `llm`, two per APM trace. The other 28 or 29 spans in each APM trace have no `gen_ai.*` attribute and are absent, as the doc says.
- **Interpretation:** The trace qualified, and `generate_dialogue` had a `gen_ai.*` attribute, so by the page's wording it should have been kept and resolved to the default kind, `workflow`. It was dropped. What the observation establishes is narrow: **a span whose only `gen_ai.*` attribute is numeric, and which has no marker, is dropped.** Two explanations fit it, and this evidence cannot tell them apart:
  1. *Per-span marker requirement.* Each span needs one of the five markers itself. The PR description's per-span wording supports this reading.
  2. *String-only scan.* `gen_ai.request.temperature` arrives as a numeric attribute (APM lists it under `metrics`, not `meta`), and the converter may look only at string attributes when deciding whether a span has any `gen_ai.*` attribute. Under this reading the page's wording is right for string attributes.

  The test that would separate them is a span in a qualifying trace that has no marker but does have a string `gen_ai.*` attribute, such as `gen_ai.request.model`. Reading 1 predicts it is dropped; reading 2 predicts it is kept as `workflow`. No such span exists in the 2026-10-02 data. Until that test runs, rely only on the narrow result: a wrapper whose `gen_ai.*` attributes are all numeric `gen_ai.request.*` values is invisible in Agent Observability. Do not assume a wrapper with a string non-marker attribute is dropped too.
- **Third-party corroboration (weak):** LiveKit's spans carried `gen_ai.request.model` and `gen_ai.usage.*` but no `gen_ai.operation.name` or `gen_ai.provider.name`, and the reporter wrote: "Because of this, Datadog doesn't detect these spans as "LLM/GenAI spans" and don't surface them in their LLM Observability service." ([livekit/agents #4639](https://github.com/livekit/agents/issues/4639), 2026-01-28, closed). That report predates the 2026-09-11 doc rule and does not say whether other spans in the trace had markers, so it is consistent with both readings rather than deciding between them.
- **Backend evidence that a relevance check exists:** "these gen_ai tags cause apm spans to be switched back to llmobs spans by spanIsRelevantForLLMObs in dd-go/trace/apps/trace-router/processors/llmobs/processor.go" ([dd-trace-py PR #20375](https://github.com/DataDog/dd-trace-py/pull/20375), merged 2026-09-16). The tags it refers to, from [PR #20083](https://github.com/DataDog/dd-trace-py/pull/20083), include `gen_ai.operation.name` and `gen_ai.provider.name`, so this confirms a server-side per-span check but does not show which attributes it tests.

**Stage 2: span kind.** 🟢 high for `chat` → `llm` (doc and observation agree); 🟡 for the rest (doc only)
- **Source says (OTel 1.37+ table):** "`generate_content`, `chat`, `text_completion`, `completion` → `llm`"; "`embeddings`, `embedding` → `embedding`"; "`execute_tool` → `tool`"; "`invoke_agent`, `create_agent` → `agent`"; "`rerank`, `unknown`, *(default)* → `workflow`". ([source](https://github.com/DataDog/documentation/blob/e91e761487cd741f49821d980b940b652afb5fc7/hugo/content/en/llm_observability/instrument/otel_instrumentation.md))
- **Fallbacks, in the doc:** "`llm.request.type` is used as a fallback when `gen_ai.operation.name` is absent" (`chat`, `completion` → `llm`; `embedding` → `embedding`; `rerank`, `unknown`, default → `workflow`). "If both `gen_ai.operation.name` and `openinference.span.kind` are present, `gen_ai.operation.name` takes precedence." `langfuse.observation.type` "is also used as a fallback for span kind resolution when `gen_ai.operation.name` is absent."
- **What does not count:** Both wrapper spans became `llm` while having no model, no provider, no token counts, no message content, OTel `span.kind: internal`, and (for `generate_summary`) a 6.7-second duration spanning a whole LangGraph node. 🟢 observed. Nothing about the span's shape is checked; the operation name alone decides. Missing model and provider produce warnings (`otel_warning_missing_model_name`, `otel_warning_missing_model_provider`) but do not change the kind.
- **Interpretation for finding 1:** The misclassification is fully explained by the agent writing `gen_ai.operation.name: chat` on a span that does not make the LLM call. Datadog trusts the attribute. Removing `chat` from the wrapper would, by Stage 1, also remove the wrapper from Agent Observability unless it keeps another marker. Setting a non-LLM operation value on it (for example `invoke_workflow`, which the table does not list) would make it a `workflow` span. M3 question 5 covers how `invoke_workflow` and `invoke_agent` are handled.

**What the doc and the observations do not settle.** 🔴 low, open
- **Precedence among the fallbacks.** The doc gives `gen_ai.operation.name` precedence over each fallback, but does not order `llm.request.type`, `langfuse.observation.type` and `openinference.span.kind` against each other when `gen_ai.operation.name` is absent. No `@traceloop/*` package sets more than one of them (M2), so this is unlikely to matter for spiny-orb.
- **Spans with a marker but no operation name.** A span with `gen_ai.provider.name` or `gen_ai.system` and no `gen_ai.operation.name` survives Stage 1 and, with no fallback, resolves to `workflow` by the default row. The doc's "Missing operation name" warning (`otel_warning_operation_missing`, "Expected `gen_ai.operation.name`") probably fires on such spans, but no observed span shows it. The old-set Traceloop packages (cohere, together, vertexai) emit `gen_ai.system` and `llm.request.type` without an operation name, so the live check or a later run should look for this warning.
- **Case sensitivity.** The doc lists lowercase values only and says nothing about `Chat` or `CHAT`. Not tested. The spec defines lowercase values, and every `@traceloop/*` package emits lowercase (M2), so this is low risk.
- **Unknown or newer operation values.** By the default row, any value not in the table becomes `workflow`, including the spec's `invoke_workflow`, `retrieval` and `plan`, and LangChain's non-spec `workflow`. That is doc-only. The warning table's fix text recommends `retriever` and `embeddings`, and `retriever` does not appear in the span-kind table, so a span following the warning's advice would also land as `workflow`, not `retrieval`. The doc is internally inconsistent here.
- **Whether a dropped ancestor re-parents its descendants.** Both observed `llm` spans have the APM parent `commit_story.ai.generate_journal_sections`, which has no `gen_ai.*` and was dropped, and both converted spans have `parent_id: undefined`. So a kept span whose parent is dropped becomes a root. Whether it would attach to a kept grandparent instead is not observed, because no grandparent was kept.

**Interpretation for M4.**
- Decision 1 has three outcomes for a wrapper span, not two. With `gen_ai.operation.name: chat` (or another LLM value), it shows as an `llm` span with "unknown" model and provider, which is finding 1. With a non-LLM marker value, such as `invoke_workflow`, it shows as a `workflow` span. With only numeric `gen_ai.request.*` attributes (such as `temperature`) and no marker, it does not appear in Agent Observability at all, and its attributes stay in APM. A wrapper with a string non-marker attribute, such as `gen_ai.request.model`, is untested: it is either dropped or kept as `workflow`, depending on which reading in Stage 1 is right. If M4 considers that placement, run that test first.
- If Traceloop's LangChain spans are exported as roots (#1038), and the wrapper is dropped or kept as a separate root, nothing in Agent Observability ties the LLM call to the wrapper. The live check should record the converted `parent_id` of every LangChain span.

### Conflicting Findings

- **Doc, attribute mapping reference:** "Spans without any `gen_ai.*` attribute are also dropped individually, even in a trace that qualifies."

- **Observed (2026-10-02, 24 APM traces):** `commit_story.ai.generate_dialogue`, with `gen_ai.request.temperature` and no marker, was dropped in a trace that qualified through two `chat` spans.
- **Interpretation:** The observation contradicts the page's wording for a span whose only `gen_ai.*` attribute is numeric. It does not show whether a string non-marker attribute would keep a span. The PR description's per-span marker wording and a string-only scan both explain it (see "Span classification (M3 question 2)", Stage 1). 🟡 medium for the narrow result, because it rests on one span name across 24 traces from one application; 🔴 low for either explanation.

- **Interpretation:** The observation wins for what the UI shows. The doc's OpenInference section says "missing provider or model values are set to `unknown`", which may be the shared behavior. 🟢 that the UI shows `unknown`.

### Caveats

- Every Datadog-specific claim here comes from Datadog's own docs, blog or docs repository. Datadog is the only primary source for its own behavior, so "two independent sources" is met only where commit-story-v2's observed run or Traceloop's docs corroborate. Elsewhere confidence is capped at medium.
- The docs repository's `hugo/` path history begins 2026-08-26 (commit `d732f0cc0b2d`, "Reorganize Agent Observability docs into task-based sections"). Earlier history sits under the pre-move path and was not read.
- In `search_llmobs_spans`, the raw query `-@span_kind:llm` was silently ignored and returned `llm` spans. Use the structured `span_kind` parameter, and run a positive control search alongside any search expected to come back empty.
- The `DataDog` GitHub org enforces SAML, so authenticated `gh api` calls fail with 403. Unauthenticated `curl` to `api.github.com` and `raw.githubusercontent.com` works for the public `DataDog/documentation` repository. Use a pinned SHA in raw URLs.
