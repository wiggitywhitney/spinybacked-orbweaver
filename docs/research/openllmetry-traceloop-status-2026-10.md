## Summary

`traceloop/openllmetry-js` is not archived or deprecated. All twelve `@traceloop/instrumentation-*` packages spiny-orb maps or lists are at **0.27.0**, published 2026-06-01. Since then the JS repository has gone quiet: the last push to `main` was 2026-06-18, fixes merged after 0.27.0 have not been released, and outside pull requests opened since July have had only bot reviews. Traceloop's GitHub organization now reads "traceloop from ServiceNow", following ServiceNow's acquisition of Traceloop in March 2026. The Python sister repository `traceloop/openllmetry` is still releasing (0.62.4 on 2026-09-29), so the slowdown is specific to the JS repository.

**The donation did not happen.** Traceloop proposed donating OpenLLMetry's instrumentations to OpenTelemetry in February 2025 (open-telemetry/community #2571). OTel closed the proposal on 2026-06-16, stating it "never landed", the same day OTel accepted Arize's OpenInference code grant. Both OpenLLMetry repositories, and every `@traceloop/*` npm package, are still owned and maintained by Traceloop.

**OpenLLMetry has not been absorbed by OTel, and OTel's own JS replacement is only partly shipped.** OTel is building first-party JS GenAI instrumentation in `opentelemetry-js-contrib`, partly by porting the donated OpenInference code (tracking issue #3668, opened 2026-08-12). As of 2026-10-05, two published OTel packages cover spiny-orb's SDK list: `@opentelemetry/instrumentation-openai` (0.20.0; 0.21.0 was published 2026-10-06 and is the version the installed-package check inspected) and Bedrock Runtime through `@opentelemetry/instrumentation-aws-sdk` (0.77.0). The OTel LangChain package exists in the repository but is `private` and unpublished. The Anthropic port is an open, unmerged PR. Nothing OTel-owned covers Cohere, Together, LlamaIndex, MCP, Vertex AI or the three vector databases. For most of spiny-orb's list, `@traceloop/*` is still the only OTel-GenAI-convention option.

**The `@traceloop/*` packages do not emit one consistent set of names, and none of them reads `OTEL_SEMCONV_STABILITY_OPT_IN`** (M2 question 3, from source at tag 0.27.0). Six packages (anthropic, openai, bedrock, langchain, llamaindex, google-generativeai) were migrated in March–April 2026 to the names in `@opentelemetry/semantic-conventions` 1.40. They emit `gen_ai.provider.name`, `gen_ai.operation.name`, `gen_ai.usage.input_tokens`/`output_tokens` and JSON `gen_ai.input.messages`/`output.messages`. Three (cohere, together, vertexai) were never migrated. They emit `gen_ai.system`, `gen_ai.usage.prompt_tokens`/`completion_tokens`, indexed `gen_ai.prompt.{N}.*`/`gen_ai.completion.{N}.*`, and no `gen_ai.operation.name`. The other four emit no LLM attributes at all: mcp uses `traceloop.*` and `mcp.*`, pinecone and qdrant use deprecated `db.system` and `db.vector.*`, and chromadb emits nothing. Each package's names are fixed, with no switch to the other set. Several packages emit spans that are not inference spans. LlamaIndex emits Traceloop-only workflow and task spans (`traceloop.span.kind`), and MCP emits `CLIENT` or `SERVER` request spans. Neither of those carries a GenAI span type. Only `@traceloop/instrumentation-langchain` emits GenAI span types other than inference. It emits `execute_tool`, `invoke_agent` for chains whose class name contains "agent" or "executor", and a non-spec `workflow` operation for every other chain. It never emits `invoke_workflow`.

**Calling `manuallyInstrument()` with no argument crashes for 12 of the 13 packages** (M2 part b, from the installed 0.27.0 `dist`, run on 2026-10-07). Only ChromaDB survives it, because its method body is empty. Every LLM and vector-database package takes the SDK module itself, so the right argument differs by package. Anthropic, Bedrock, Vertex AI, Cohere, LlamaIndex, Pinecone and Qdrant need the module namespace (`import * as`). OpenAI and Together need the default export. MCP needs `{ Client }` or `{ Server }`. google-generativeai needs the CommonJS module, because it cannot patch an ESM namespace. LangChain needs `{ callbackManagerModule }`. The installed code also confirmed the attribute-name split and the LangChain span shapes above. A real LangChain run reproduced the missing parent links that issue #1038 reports. With an enclosing application span, LangChain's spans nest under it as siblings. Without one, each span is the root of its own trace. The cause is in the code: the handler starts every span from the active context and never uses `parentRunId`. Content capture is not uniform. Most packages capture by default and turn it off with `traceContent: false`, Qdrant captures only with `traceContent: true`, Pinecone has no switch, and OpenAI's `logprobs` event ignores the setting.

## Surprises & Gotchas

- 🟢 **`@traceloop/instrumentation-langchain` 0.27.0 never links LangChain's spans to each other. They are separate roots unless an application span encloses the call.** An open issue filed 2026-09-28 reported this with a reproduction under `@traceloop/node-server-sdk`. The M2 part (b) check reproduced it in spiny-orb's setup on 2026-10-07: the standalone package, a user-owned tracer provider with `AsyncLocalStorageContextManager`, `@langchain/core` 1.2.17, and a `FakeListChatModel` called inside a `RunnableLambda`. When the chain ran inside an application span `app.wrapper`, both `workflow RunnableLambda` and `chat FakeListChatModel` had `app.wrapper` as their parent. They were siblings, so the chat span did not nest under the chain span. With no enclosing span, the two spans landed in two different traces, each with `parent=none`. The cause is in `dist/index.js`: every handler method calls `this.tracer.startSpan(...)` with the active context, and none uses its `_parentRunId` argument. LangChain invokes callbacks outside the parent run's OTel context. So in a commit-story-style setup, where spiny-orb's agent wraps a LangGraph node in an application span, LangChain's spans attach to that wrapper, but the graph's own chain structure is flattened. For a LangGraph run with no application span around it, the trace splits apart. M3's live check should still record parent IDs on a real hook-triggered run.
  **Source says:** "every span produced by a single LangChain invocation is exported as its **own root span in its own trace**. The chain, chat-model and tool spans are never linked as parent/child" ([openllmetry-js issue #1038](https://github.com/traceloop/openllmetry-js/issues/1038))
  Reproduction script: `/tmp/llm-check-scripts/langchain-spans.mjs` and `langchain-spans-noparent.mjs` (local only, not committed).
- 🟢 **The LangChain chain handler reads `@langchain/core` 1.x callback arguments in the wrong positions, so a chain's `runName` is dropped.** The handler's code comment says "Parameter order follows @langchain/core >=1.0.0", and its signature is `handleChainStart(chain, inputs, runId, _runType, _tags, _metadata, runName, _parentRunId, _extra)`. But installed `@langchain/core` 1.2.17 calls `handler.handleChainStart?.(chain, inputs, runId, this._parentRunId, this.tags, this.metadata, runType, runName, extra)` (`dist/callbacks/manager.cjs` L391). Traceloop's `runName` therefore receives `runType`, which is undefined for ordinary chains, and the span falls back to the class name. In the reproduction, a chain configured with `runName: 'summarize_node'` produced a span named `workflow RunnableLambda`, with `traceloop.workflow.name: RunnableLambda`. For LangGraph, this likely means node spans carry class names instead of node names. That is an interpretation, not checked on a real graph. The chat-model and tool handlers' argument orders do match core 1.2.17.
- 🟢 **Calling `manuallyInstrument()` with no argument throws for 12 of the 13 packages, not only LangChain.** It was run on each installed 0.27.0 class on 2026-10-07. Only `ChromaDBInstrumentation` survives, because its body is empty. So commit-story-v2's `new McpInstrumentation().manuallyInstrument()` throws `TypeError: Cannot read properties of undefined (reading 'Client')`, the same failure class as finding 3. Each package's correct argument is in the installed-package table below.
- 🟢 **spiny-orb's MCP class name does not exist.** `@traceloop/instrumentation-mcp` 0.27.0 exports only `McpInstrumentation`. `src/languages/javascript/ast.ts` maps `@modelcontextprotocol/sdk` to `importName: 'MCPInstrumentation'`, and the prompt tables use the same spelling. An ESM `import { MCPInstrumentation } from '@traceloop/instrumentation-mcp'` fails at link time, and a CommonJS destructure gives `undefined`. commit-story-v2's `McpInstrumentation` is correct. This is an input for M4 decision 3 and M5.
- 🟢 **The LangChain constructor patches `CallbackManager` by itself.** `new LangChainInstrumentation()` calls `instrumentCallbackManagerDirectly()`, which runs both `require("@langchain/core/callbacks/manager")` and `import(...)` of the same path, from the instrumentation package's own location, and patches both copies. In the reproduction, the ESM `CallbackManager` was patched before `manuallyInstrument` was called. `manuallyInstrument({ callbackManagerModule })` is a second path for when `@langchain/core` resolves to a different copy than the one the instrumentation sees. A guard flag (`_traceloopPatched`) prevents double patching. `manuallyInstrument({})` is also safe, and does nothing.
- 🟡 **The LangChain instrumentation has an open, unreleased bug that drops inherited callback handlers and doubles spans.** Issue #1016 has been open since 2026-06-02. The fix PR (#1029, opened 2026-07-07) has had no human review.
  **Source says:** "It also added a new `TraceloopCallbackHandler` unconditionally, duplicating it on child runnable invocations and doubling emitted spans." ([openllmetry-js PR #1029](https://github.com/traceloop/openllmetry-js/pull/1029))
  **Source says:** "[BUG] [instrumentation-langchain] _configureSync patch drops non-array inheritableHandlers and duplicates TraceloopCallbackHandler" (issue #1016 title, open, read via `gh api repos/traceloop/openllmetry-js/issues/1016`)
- 🟢 **Fixes on `main` since 0.27.0 are unreleased.** Three are merged and unreleased: #1014 (OTel experimental dependency bump, 2026-06-17), #1028 (cache tokens included in `gen_ai.usage.input_tokens`, 2026-06-18) and #1026 (cache-token attributes for OpenAI, Bedrock, Together AI and Vertex AI, 2026-06-18). Published 0.27.0 still declares `"@opentelemetry/instrumentation": "^0.203.0"`. The vulnerability #1014 targets is in `@opentelemetry/sdk-node`, which only `@traceloop/node-server-sdk` pulls in. spiny-orb recommends individual instrumentation packages, not that SDK, so that specific vulnerability does not reach spiny-orb's recommended set.
  **Source says:** "only **one** has ever reached consumers in an unfixed state: **`@opentelemetry/sdk-node`** (high — Prometheus exporter crash), declared `^0.203.0` on `main`" ([openllmetry-js PR #1014](https://github.com/traceloop/openllmetry-js/pull/1014))
- 🟢 **spiny-orb's own mapping has two gaps against the current package list.** These are local findings, not web research. (1) `src/languages/javascript/ast.ts` `FRAMEWORK_TO_LIBRARY` (lines 195–206) has no LangChain entry, even though both prompt tables list `@traceloop/instrumentation-langchain`. So the deterministic `librariesNeeded` path never records LangChain, and only the LLM can. (2) The repository ships `instrumentation-google-generativeai` (added in v0.26.0 with "OTel 1.40 GenAI semantic conventions"), which neither spiny-orb table lists. Both are inputs for M4 decision 3.
- 🟢 **`@traceloop/instrumentation-chromadb` is a no-op, and has been since December 2024.** At 0.27.0, 275 of the 351 lines in `src/instrumentation.ts` are commented out. `wrap` and `unwrap` return the module unchanged, and `manuallyInstrument` has an empty body, so the package patches nothing and emits no spans. The commenting-out came in commit `0f18865c42` ("fix(deps): major, minor and various instrumentation fixes", 2024-12-16), and no later commit touches the file. spiny-orb's `ast.ts` maps `chromadb` to this package. This is two sources in the sense that the tagged file and the file's commit history agree, but both come from the same repository. The installed 0.27.0 `dist` (`dist/src/index.js` L37–L66) confirms it: `wrap` and `unwrap` contain only commented-out `_wrap` calls and `return module`, `manuallyInstrument` contains only two commented-out lines, and `manuallyInstrument()` with no argument returns without error. This is directly relevant to finding 4 (recommended libraries emitting no spans) and to M4 decisions 3 and 5.
  **Source says:** `public manuallyInstrument(module: typeof chromadb) {` followed by only commented-out lines, and `private wrap(module: typeof chromadb) { ... return module; }` ([instrumentation-chromadb/src/instrumentation.ts @ 0.27.0](https://github.com/traceloop/openllmetry-js/blob/8b37d7e85ec21770e5ccc8290cbfbd0079a492f7/packages/instrumentation-chromadb/src/instrumentation.ts#L39-L80))
- 🟢 **Standalone instrumentations ignore `TRACELOOP_TRACE_CONTENT`, and the LLM packages capture prompt and completion content by default.** The environment variable is read in exactly one place, `@traceloop/node-server-sdk`'s `shouldSendTraces()`. When it is `false`, that SDK pushes `traceContent: false` into each instrumentation's config. The installed 0.27.0 `dist` (CJS and ESM builds) of all 13 instrumentation packages contains no `process.env`, `TRACELOOP_TRACE_CONTENT` or `OTEL_SEMCONV_STABILITY_OPT_IN` string. spiny-orb's setup uses individual instrumentations under a user-owned NodeSDK, so setting `TRACELOOP_TRACE_CONTENT=false` there turns nothing off. The only switch is the `traceContent` constructor option. Traceloop's docs say otherwise (see Conflicting Findings). It feeds M4 decision 6 and M5.
  **Corrected 2026-10-07 from the installed code:** "each one falls back to `traceContent ?? true`" holds for the ten LLM and MCP packages, but not for every package.
  - `@traceloop/instrumentation-qdrant` tests `if (this._config.traceContent)`, so request and result details are recorded only when `traceContent: true` is set.
  - `@traceloop/instrumentation-pinecone` has no `traceContent` handling. It always records query vectors, metadata filters, result IDs, scores, values and metadata.
  - `@traceloop/instrumentation-openai` adds a `logprobs` span event, whose payload includes each output `token`, whenever the response has logprobs. That call is not gated by `traceContent`, so `traceContent: false` does not fully stop output text from being captured when the app requests logprobs.
  - Pinecone and Qdrant call `setAttribute` on the return value of `span.addEvent(...)`. The OTel API declares `addEvent(...): this`, so those "event attributes" land on the span itself, and the events carry only names.
  **Source says:** `(process.env.TRACELOOP_TRACE_CONTENT || "true").toLowerCase() === "false"` ([traceloop-sdk/src/lib/tracing/index.ts @ 0.27.0, L361–L383](https://github.com/traceloop/openllmetry-js/blob/8b37d7e85ec21770e5ccc8290cbfbd0079a492f7/packages/traceloop-sdk/src/lib/tracing/index.ts#L361-L383)); and in each instrumentation, `return this._config.traceContent !== undefined ? this._config.traceContent : true;` (for example [instrumentation-langchain/src/instrumentation.ts L128–L135](https://github.com/traceloop/openllmetry-js/blob/8b37d7e85ec21770e5ccc8290cbfbd0079a492f7/packages/instrumentation-langchain/src/instrumentation.ts#L128-L135)). GitHub code search for `TRACELOOP_TRACE_CONTENT` in the repository returns only the SDK file.
- 🟡 **LangChain's chain spans set `gen_ai.provider.name: "langchain"` and a non-spec `gen_ai.operation.name: "workflow"`.** Every LangChain chain run that is not detected as an agent becomes an `INTERNAL` span named `workflow {runName}`. Because LangGraph runs each node and the compiled graph as LangChain runnables, that likely includes every LangGraph node (an interpretation, not checked on a real run). The spec's operation value for this is `invoke_workflow`, and the spec defines no `gen_ai.provider.name` on workflow or internal agent spans. Spec issue #178 calls copying a provider onto an enclosing span a leak of "implementation details of the inner LLM call". A backend that keys on `gen_ai.provider.name` or `gen_ai.operation.name` could therefore treat these spans as LLM spans, which is finding 1's failure mode, now emitted by the library rather than by spiny-orb's agent. This is 🟡 because the source code is the only JS-specific source. M3's live check should record what Datadog does with these spans.

### Donation status (M2 question 1)

🟢 **High (two independent sources: the OTel proposal's closing comment, and the current ownership of both repositories and the npm packages).** OpenLLMetry was proposed for donation to OpenTelemetry, and the proposal was closed without a donation.

**Proposed to whom, and what.** GitHub user `nirga`, writing for Traceloop, opened [open-telemetry/community #2571, "[Donation Proposal]: OpenLLMetry"](https://github.com/open-telemetry/community/issues/2571) on 2025-02-13. It was labeled `area/donation` on 2025-02-17.
- **Source says:** "Traceloop would like to offer the donation of OpenLLMetry instrumentation packages to the OpenTelemetry project." and "As we standardize GenAI semantic conventions we'd like to gradually donate mature instrumentations back to the OpenTelemetry eco-system where they can be co-maintained by us and the rest of the community" (issue #2571 body, read via `gh api repos/open-telemetry/community/issues/2571`)
- The proposal's **Repository** field lists only `https://github.com/traceloop/openllmetry`, the Python repository. It never mentions `traceloop/openllmetry-js`. A search for `openllmetry-js` donation proposals across the `open-telemetry` GitHub organization (`gh api search/issues -f q="org:open-telemetry openllmetry-js"`) found none.

It tests the serialized class name, not the run name, so a LangGraph node named `agent` does not count.

**Partial corroboration (Python, not JS):** **Source says:** "**The langchain instrumentor labels the root chain span `invoke_agent`, not `invoke_workflow`**, even though it tags that same span `traceloop.span.kind = workflow`." ([dynatrace-oss/dynatrace-ai-agent-instrumentation-examples #236](https://github.com/dynatrace-oss/dynatrace-ai-agent-instrumentation-examples/issues/236), 2026-08-10, about Python `opentelemetry-instrumentation-langchain` 0.62.x, read "from the installed SDK sources"). This independently confirms that Traceloop's LangChain instrumentation emits no `invoke_workflow` span. The JS and Python packages differ in which value they use instead.

**No LangGraph-specific support.** The feature request [openllmetry-js #476, "Add support for LangGraph Framework"](https://github.com/traceloop/openllmetry-js/issues/476), has been open since 2024-12-17. The JS source has no `langgraph` reference. **Source says (Whitney's own comment on #476, 2026-01-29, using `@traceloop/node-server-sdk` v0.22.6):** "What's happening is that tool spans end up in completely separate traces instead of nesting under the workflow span." and "OpenLLMetry successfully creates spans for the LangGraph workflow (`CompiledStateGraph.workflow`)". That matches issue #1038's parentless-spans report in Surprises. It also shows the compiled graph getting a chain span, though under 0.22.6's older span naming. Because the comment is Whitney's, it is not independent of this project.

**Interpretation.**
- **Answer to M2's LangChain sub-question.** `@traceloop/instrumentation-langchain` 0.27.0 emits more than inference spans. It also emits internal `invoke_agent` spans for agent-class chains, `execute_tool` spans, and `workflow`-operation spans for every other chain. It never emits `invoke_workflow`. The constant `GEN_AI_OPERATION_NAME_VALUE_INVOKE_WORKFLOW` is defined in semconv JS 1.43.0 but not in 1.40.0, the version this package targeted. That likely explains the custom value: the package predates the constant's arrival in JS.
- **For M4 decision 1.** With LangChain instrumentation active, the library itself puts `gen_ai.operation.name` and `gen_ai.provider.name` on non-inference chain spans, with values a backend may not expect. If spiny-orb's agent also adds a wrapper span around a LangGraph node, a trace could carry three layers: spiny-orb's wrapper, LangChain's `workflow {node}` span and LangChain's `chat {model}` span. Given issue #1038, the last two may not even nest under the first. Decision 1 should treat the library's chain spans as part of what spiny-orb's wrapper sits next to.
- **Double instrumentation.** `ChatAnthropic` calls `@anthropic-ai/sdk` underneath. If `@traceloop/instrumentation-langchain` and `@traceloop/instrumentation-anthropic` are both active, one model call likely produces two `chat` inference spans, one from each package. This is an interpretation, not observed. It is the same one-instrumentation-per-SDK concern as above, but here it is between two `@traceloop/*` packages, and it matters for M4 decision 3. spiny-orb's `ast.ts` maps `@anthropic-ai/sdk` imports, but not `@langchain/anthropic`.

## Conflicting Findings (M2 question 3)

- **Traceloop's docs say the content setting reaches individual instrumentations.** **Source says:** "To disable logging, set the `TRACELOOP_TRACE_CONTENT` environment variable to `false`." and "OpenLLMetry SDK, as well as all individual instrumentations will respect this setting." ([traceloop/docs `openllmetry/privacy/traces.mdx`](https://github.com/traceloop/docs/blob/abd8e4aa4a98b544265e9464d85299f8a46467ad/openllmetry/privacy/traces.mdx))
- **Traceloop's code says they do only through the SDK.** The variable is read only in `traceloop-sdk/src/lib/tracing/index.ts`, and instrumentations default to `traceContent ?? true` (see Surprises).
- **Interpretation:** the code is authoritative for spiny-orb's setup. An instrumentation "respects" the variable only when `@traceloop/node-server-sdk` constructs it. Without that SDK, the variable does nothing. Part (b) confirms this against installed `dist`.

- **Traceloop's docs list old attribute names for all LLM spans.** **Source says:** "`gen_ai.system` - Provider name (OpenAI, Anthropic, etc.)", "`gen_ai.prompt.{N}.content` - Prompt messages" and "`llm.usage.total_tokens` - Total tokens" ([traceloop/docs `openllmetry/integrations/elasticsearch-apm.mdx`, L229–L247](https://github.com/traceloop/docs/blob/abd8e4aa4a98b544265e9464d85299f8a46467ad/openllmetry/integrations/elasticsearch-apm.mdx?plain=1#L229-L247), docs repository last pushed 2026-07-10)
- **The code says this holds only for cohere, together and vertexai.** The six migrated packages emit `gen_ai.provider.name`, JSON `gen_ai.input.messages` and `gen_ai.usage.total_tokens` instead (see the per-package table).
- **Interpretation:** the docs predate the March–April 2026 migrations and were not updated. Do not use Traceloop's docs as a source for attribute names. Read the package source or the installed `dist`.
